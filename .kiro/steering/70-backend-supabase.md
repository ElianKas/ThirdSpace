# Backend (Supabase)

> Split out of the former `architecture.md`.

- Supabase is the backend. The supabase-kt SDK (GoTrue auth + Postgrest, 3.8.0; Ktor 3.5.1; kotlinx-serialization/coroutines 1.11.0) lives in the SHARED module. All supabase-kt / Ktor / coroutine / `suspend` / `Flow` types stay INTERNAL to shared — only flat types and callback-based hooks cross `FeedBridge`. The bridge's suspend/Flow/supabase work runs on a background `Dispatchers.Default` scope; only the final flat callback/listener is delivered on the main thread (via the `onMain` helper), consistent with the flat-boundary rule.
- Auth: email/password sign-up, sign-in, sign-out, and session restore via a shared `AuthRepository` over GoTrue, exposed through a flat callback-based bridge (completions of `Bool`/`String`; an `observeAuth` listener). An `@Observable` Swift `Session` wrapper (mirrors the `Localization` pattern) drives the AUTH GATE in `ContentView` (auth screens when logged out, `RootTabView` when logged in). Sign-up passes name/city in the user metadata so the DB trigger populates the profile.
- Keys/config: the PUBLIC publishable key (`sb_publishable_…`) + project URL come from a gitignored `iosApp/Supabase.xcconfig` (seeded from the committed `Supabase.xcconfig.template`), surfaced into Info.plist as `SupabaseURL` / `SupabasePublishableKey`, read at launch and injected via `FeedBridge.configureSupabase(url:publishableKey:)`. The URL is stored host-only (xcconfig `//` caveat; Swift re-adds the scheme). The secret/service-role key NEVER ships in the client. (Current terminology: Supabase's PUBLISHABLE key replaced the older "anon" key.)
- DB schema: SQL migrations under the repo-root `supabase/` dir (profiles + spots + posts/comments/votes) with the signup→profile trigger, `updated_at` triggers, and self-contained RLS (`spots` readable by any authenticated user; insert/update/delete own via `owner_id = auth.uid()`). The user provisions their own project and applies the migrations (`supabase link` + `supabase db push`).
- SQLDelight cache migrations: schema changes to the SQLDelight cache DB (`ThirdSpaceDb`) require a migration file at `shared/src/commonMain/sqldelight/com/example/thirdspace/db/migrations/<fromVersion>.sqm`, which auto-bumps the generated schema version so an existing on-device DB is migrated in place rather than crashing with `no such table`. The `.sq` continues to describe the current schema for fresh installs; `deriveSchemaFromMigrations` stays OFF. The current schema version is 4 (`1.sq` = v1, `1.sqm` → v2, `2.sqm` → v3, `3.sqm` → v4; `2.sqm` added the `cachedPosts.kind` column, `3.sqm` added `author_user_id` to `cachedPosts` + `cachedComments`). Collections intentionally add NO SQLDelight cache and NO `.sqm` (they use an in-memory seam like the follow/profile seams), so the schema version stays 4.
- Feed (posts / comments / votes) is backed by Supabase. Reads go through the `feed_entries` UNION VIEW (posts PLUS bare spots that have no post), NOT only `post_feed`. The flat boundary carries a `kind: String` ("post"/"spot") discriminator; bare-spot cards hide the vote control, comment button, and caption (`PostCardView` `isBareSpot`) while keeping the spot header. `post_feed` remains the source for the UNION's post branch and for the profile's own-posts (joins posts + profiles + spots; real `score` = sum of `post_votes`; the caller's own `my_vote` via `auth.uid()` under `security_invoker`). Writes: `createPost` inserts into `posts` (requires an existing `spot_id`; empty caption allowed as a pure check-in); `vote` writes `post_votes` (value CHECK ±1; clearing a vote DELETEs the row); comments insert into `post_comments`. All write paths are offline-first through `FeedCache` (SQLDelight) with outbound queues — `pendingPostInserts`, `pendingVotes` (latest-intent-wins per post), `pendingCommentInserts` — flushed on the next authenticated refresh; optimistic local rows are reconciled by a destructive replace-all on the post-push refresh. Comment author names resolve via a PostgREST `profiles(name)` embed with an honest empty-string fallback. Relative timestamps use the self-contained `RelativeTime` formatter, not the i18n `Strings` layer.
- Profile: the current user's own `profiles` row is read + edited via a shared `ProfileRepository` with an IN-MEMORY single-row cache (side-effect-free reads + explicit refresh, mirroring the feed/spots seams — NO SQLDelight / `.sqm` for the single row). Reads go through the bridge's flat `profile()` / `loadProfile` / `observeProfile`; `updateProfile(name,city,bio)` writes the own row under the existing RLS "update own" policy (optimistic in-memory update; offline/unauth reports failure, NO durable queue). The profile's `spotCount`/`postCount` are the real counts of the user's own `spots`/`posts`, DERIVED from the fetched own-content list sizes; its "meine Posts"/"meine Spots" tabs show the user's OWN rows (`post_feed` where `author_id == uid` / `spots` where `owner_id == uid`), reusing the shared `PostFeedMapping` / `SpotDtoMapping`. `username` is derived (email local-part; no DB column), `monthYear` is derived from `created_at`, and `bio` is a `profiles` column added by the `profile_add_bio` migration. The profile cache is reloaded/cleared driven by the iOS `ContentView`'s auth-state changes (`.onChange(of: session.isAuthenticated)` + `.onAppear`): sign-out clears the in-memory profile cache via a flat `FeedBridge.clearProfile()` → `Profiles.clear()` → `ProfileRepository.clear()`, so a different user signing in on the same launch never sees the prior user's profile/posts/spots (cross-user data-leak fix). The profile screen also has native pull-to-refresh (`ProfileView` `.refreshable`), analogous to the feed. `followerCount`/`followingCount` are the REAL counts of the current user's social graph, fetched from the `follows` table during the profile refresh and folded onto the cached `Profile` by `ProfileRepository` via injected follow-count providers (the same way spot/post counts are injected).
- Follow (social graph): a one-directional follow graph backed by a new `follows` table (migration `20260101000009_init_follows.sql`) — columns `follower_id`/`following_id` (both FK `auth.users` ON DELETE CASCADE) + `created_at`, a composite PK `(follower_id, following_id)` guaranteeing uniqueness + idempotent re-follow, a CHECK (`follower_id <> following_id`) preventing self-follow, and self-contained RLS (read-all to authenticated; insert/delete own via `follower_id = auth.uid()`; no UPDATE); two indexes back the followers-of / following-of list + count queries. The shared seam is a `FollowRepository` + `Follows` provider (mirrors `Profiles`/`Feed`: in-memory cache, side-effect-free pure reads, explicit refreshes on a background `Dispatchers.Default` scope with an in-flight coalesce guard, optimistic follow/unfollow with NO durable queue — offline/unauth keeps the optimistic state but reports `false`) over a `SupabaseFollowRepository` (`FollowRemoteSource`) using only proven Postgrest API — a client-side join (follow rows, then per-id `profiles` reads) rather than a two-FK embed, and `.decodeList().size` counts rather than `Count.EXACT`; the flat `FollowUser(id, name, username, city, isFollowedByMe)` model crosses the boundary as `IosFollowUser`. `SupabaseProfileRepository` was generalized with `fetchProfile(userId)` so ANY user's profile row can be read (not just the current user's). Live follow data still requires the user to apply the new migration + a logged-in session.
- Collections (personal spot collections): PERSONAL, owner-scoped spot collections backed by two new tables (migration `20260101000010_init_collections.sql`) — `collections` (id, `owner_id` FK `auth.users` ON DELETE CASCADE, name, created_at, updated_at + a `set_updated_at` trigger reused from the profiles migration) and a `collection_spots` many-to-many join (`collection_id` FK `collections` ON DELETE CASCADE, `spot_id` FK `spots` ON DELETE CASCADE, created_at, composite PK `(collection_id, spot_id)` for uniqueness/idempotent re-add; insert/delete only, no UPDATE). OWNER-SCOPED RLS (these are PRIVATE, unlike the read-all `spots`/`follows` tables): `collections` read/insert/update/delete gated `owner_id = auth.uid()`; the join table has no owner column so its RLS gates every op via an EXISTS against the parent collection's ownership. Indexes on `owner_id` + `collection_id` + `spot_id`. The shared seam is a `CollectionRepository` + `Collections` provider (mirrors `Follows`/`Profiles`: in-memory cache — NO SQLDelight — side-effect-free pure reads, explicit `Mutex`-coalesced refreshes on a background `Dispatchers.Default` scope, optimistic create/rename/delete/add-spot/remove-spot with NO durable queue — offline/unauth keeps the optimistic state but reports `false`; an optimistic create uses a local `temp-` id reconciled by a refresh on success) over a `SupabaseCollectionRepository` using only proven Postgrest API — a client-side join (fetch `collection_spots` rows then per-id resolve against `spots` reusing `SpotDtoMapping`) rather than an embed, and `.decodeList().size` counts rather than `Count.EXACT`; the flat `SpotCollection(id, name, spotCount, createdAtLabel)` model crosses the boundary as `IosSpotCollection`. Public/shared collections and an offline collection cache are DEFERRED; live collection data requires the user to apply the new migration + a logged-in session.
- Cache reads are SIDE-EFFECT-FREE: `getPosts`/`getComments`/`getSpots` only read the local cache and never trigger a remote fetch. A remote refresh is triggered ONLY explicitly — the bridge `loadFeed`/`loadComments`/`refreshSpots` hooks, pull-to-refresh, and a single reconciling refresh after a successful write push — coalesced by an in-flight guard.
- The one-directional follow graph IS implemented (see the Follow seam above). Deliberately deferred on the backend: Realtime, spot update/delete sync, advanced conflict resolution, and the broader legacy social graph (friendships (symmetric)/notifications/moments/DMs/moderation) are NOT implemented.
