# Architecture & Native iOS Conventions

This document records the long-lived architecture, module boundaries, and native-UI conventions for the ThirdSpace project.

## Architecture principle

- iOS UI is fully native SwiftUI (in `iosApp/iosApp/`). There is no Compose-Multiplatform UI.
- The `shared` module is Kotlin Multiplatform LOGIC/DATA ONLY — no Compose dependency. The Android target remains, but `androidApp` is currently a non-functional placeholder; a native Android UI comes in a later phase. Business/shared logic stays in the shared module so Android can adopt it later.

## Module & package boundaries

- Shared logic/data lives in package `com.example.thirdspace.data` (commonMain): `Models.kt`, `SampleData.kt`, `Formatting.kt`, `SpotCategory.kt`, `SpotRepository.kt`, plus the backend seam — `AuthRepository.kt`, `SupabaseClientProvider.kt`, `SpotCache.kt`, `CachingSpotRepository.kt`, `SupabaseSpotRepository.kt`, `SpotMapping.kt`, the feed seam — `FeedModels.kt`, `FeedRepository.kt` (which holds `FeedRepository`/`CommentRepository`/`VoteRepository` + the `Feed` provider), `FeedCache.kt`, `SupabaseFeedRepository.kt`, `FeedMapping.kt`, `RelativeTime.kt`, the profile seam — `ProfileRepository.kt` (which holds `ProfileRepository` + the `Profiles` provider) and `SupabaseProfileRepository.kt` (which holds `ProfileDto`/`ProfileRemoteSource`/`ProfileMapping`/`SupabaseProfileRepository`), the follow seam — `FollowModels.kt`, `FollowRepository.kt` (which holds `FollowRepository` + the `Follows` provider) and `SupabaseFollowRepository.kt` (which holds `FollowRemoteSource`/`SupabaseFollowRepository`), the collection seam — `CollectionModels.kt`, `CollectionRepository.kt` (which holds `CollectionRepository` + the `Collections` provider) and `SupabaseCollectionRepository.kt` (which holds `CollectionRemoteSource`/`SupabaseCollectionRepository` + the collection DTOs) — and the `expect` declarations `SpotDbDriver.kt` / `Clock.kt` (with `iosMain`/`androidMain` actuals). The SQLDelight schema lives at `shared/src/commonMain/sqldelight/com/example/thirdspace/db/ThirdSpaceDb.sq`.
- The Swift↔Kotlin boundary goes through `FeedBridge` (shared `iosMain`). Only flat, ObjC-friendly types cross it: String / Int / Bool / Double (e.g. spot `lat`/`lng`); colors as `#RRGGBB` strings; Kotlin enums exposed as String; NO nullables and NO Long across the boundary. The generated framework is named `Shared`.
- The flat boundary now also carries CALLBACK-based hooks (auth completions/listeners, spots refresh/observe) — still flat: `Bool`/`String` completions or no-arg closures, always delivered on the main thread. All `suspend` / `Flow` / supabase-kt / Ktor / SQLDelight types stay INTERNAL to the shared module and never cross.
- The flat boundary also carries a `kind` discriminator and a NEW non-null flat `authorUserId: String` on `IosPost`/`IosComment` (the post/comment author's uid, `""` when unknown; used to open an author's profile), a flat `IosFollowUser` list type, a flat `currentUserId(): String` getter, and the follow callback hooks (`followUser`/`unfollowUser` `Bool` completions; `loadFollowers`/`loadFollowing`/`loadFollowState`/`loadFollowCounts` no-arg completions; an `observeFollows` listener; `otherProfile`/`loadOtherProfile`) — all flat (`String`/`Int`/`Bool` + `IosFollowUser`), all callbacks delivered on the main thread via `onMain`, no suspend/supabase type crossing. The boundary also carries a flat `IosSpotCollection(id, name, spotCount, createdAtLabel)` type and the collection callback hooks (`collections`/`spotsInCollection`/`collectionsContaining`/`isSpotInCollection` pure reads; `loadCollections`/`loadSpotsInCollection`/`loadMembership` refreshers; `createCollection`/`renameCollection`/`deleteCollection`/`addSpotToCollection`/`removeSpotFromCollection` optimistic `Bool` completions; an `observeCollections` listener) — all flat (`String`/`Int`/`Bool` + `IosSpotCollection`/`IosSpot`), delivered on the main thread via `onMain`, no suspend/supabase crossing.
- Boundary threading: all suspend/Flow/supabase-kt/Ktor work in the bridge runs on a background `Dispatchers.Default` scope — NEVER on `Dispatchers.Main` (running it on Main froze the iOS UI thread, e.g. GoTrue `awaitInitialization`/network). Only the final flat callback/listener is hopped onto the main thread via `withContext(Dispatchers.Main)` (the `onMain` helper), so Swift `@Observable`/`@State` mutations stay main-thread-safe.

## Native UI conventions

- No external UI library; use built-in SwiftUI controls, custom components, and SF Symbols.
- Design tokens are centralized in Swift in the `AppColor` enum (mirrored from the shared color values), together with a `Color(hex:)` initializer. Do not hardcode hex color literals inside views — reference `AppColor`.
- Reusable building blocks currently in place: `PostCardView`, `AvatarView`, `VoteControlView`, `FilterChipView`, `MapboxMapView`, `AddSpotSheetView`, `CreatePostView`, `CommentsSheetView`, `ProfileEditView`, `OtherProfileView`, `FollowListView`, `MapSpotSheetView`, `CollectionPickerSheetView`, `CollectionDetailView`, the `ScrollOffsetTracking` helper, and the auth screens `LoginView` / `SignUpView` / `AuthComponents`. Collections are backed by a `CollectionsStore` `@Observable` env wrapper (mirrors the `Session`/`Localization` pattern) with a `UISpotCollection` Swift mirror of the flat `IosSpotCollection`.
- Auth state is held in an `@Observable` Swift `Session` wrapper (mirrors the `Localization` pattern, injected into the environment) which drives the AUTH GATE in `ContentView`: auth screens when logged out, `RootTabView` when logged in.
- The feed uses a `List` with native `.refreshable` pull-to-refresh. The `ScrollOffsetTracking` helper is reserved for a future auto-hide header step.
- Sheet pattern: present sheets via `.sheet(item:)` + `.presentationDetents` + a visible drag indicator (reference implementation: `SpotSheetView`). AddSpot (`AddSpotSheetView`), CreatePost (`CreatePostView`), and Comments (`CommentsSheetView`) all follow this pattern rather than inventing their own.
- Borderless pages (those using `.ignoresSafeArea(edges: .top)`) place interactive top chrome via the reusable `.topChrome` modifier / `AppLayout.topChromeSpacing` token (in `AppLayout.swift`) rather than reading `safeAreaInsets` manually inside the ignored subtree (which returns 0). `AppLayout` is the central iOS layout-token location, analogous to `AppColor`.

## Internationalization (i18n)

- Static UI text lives in a shared i18n layer (package `com.example.thirdspace.i18n`): an `AppLanguage` enum (DE default, EN), a `Strings` interface with `De`/`En` implementations, and `AppStrings` as the single resolution point. The shared module is the single source of truth for all static strings (Android inherits them later).
- The Swift↔Kotlin boundary stays flat: `FeedBridge` exposes a flat `IosStrings` snapshot (simple keys as String properties; pluralized/interpolated strings as functions). The `AppLanguage` enum never crosses the boundary — the language code crosses as a String ("de"/"en").
- Swift reads strings through an `@Observable Localization` wrapper injected into the environment; views use `@Environment(Localization.self) private var loc` and `loc.strings.*`. Changing the language live (via `Localization.setLanguage`) re-renders observing views.
- Adding a language = one `AppLanguage` enum case + its values; the typed `Strings` interface forces every key to be provided (compile-time completeness). A commonTest asserts every key is non-empty in both languages.
- The spot→post prompt added three static keys plus one interpolated function (title / body / not-now / post labels) in both DE and EN, consistent with the typed-`Strings` completeness rule.
- The follow feature added six static keys (`followButton` / `unfollowButton` / `followListFollowersTitle` / `followListFollowingTitle` / `followSearchPlaceholder` / `followEmpty`) in both DE and EN, consistent with the typed-`Strings` completeness rule.
- The collections feature added 11 static keys (`collectionsTabTitle` / `newCollection` / `collectionNamePlaceholder` / `createCollection` / `saveToCollection` / `addToCollection` / `removeFromCollection` / `renameCollection` / `deleteCollection` / `emptyCollections` / `emptyCollectionSpots`) plus one plural function `collectionSpotCount(count)`, all in both DE and EN, consistent with the typed-`Strings` completeness rule.
- The in-app language picker is the `globe` button at the top-right of the Profile main page; the chosen language is in-memory only (NOT persisted across relaunch), default DE.
- Language display names are endonyms ("Deutsch"/"English") and are NOT translated. Dynamic/user content is NOT translated either: spot names, categories, neighborhoods, post/comment text, author names, date labels, the current email, etc.

## Navigation

- The app shell is a native SwiftUI `TabView` with four tabs: Posts (feed), Map, Discover (inert placeholder), Profile.
- Only the Profile tab is wrapped in a `NavigationStack`, so the profile can PUSH sub-pages (e.g. the "Profil bearbeiten" edit page). Other tabs are not wrapped.
- Modal surfaces use the sheet pattern (`.sheet(...)` + `.presentationDetents` + `.presentationDragIndicator(.visible)` set at the call site). Push vs. sheet: detail/compose surfaces are sheets; the profile edit page is a push sub-page.
- Another user's profile is viewable via `OtherProfileView` (a follow/unfollow button + follower/following counts) and searchable follower/following lists via `FollowListView`. These are reached by PUSH inside the Profile tab's `NavigationStack` (from the profile stat columns) and by a `NavigationStack`-wrapped SHEET from the feed/comments author taps (which are not in a `NavigationStack`).
- The Profile segmented control now has a THIRD tab, "Sammlungen" (collections), listing the user's collections; tapping one PUSHES `CollectionDetailView` (manage: remove spot, rename, delete) inside the Profile tab's `NavigationStack`, and a new collection is created inline. The collection picker (`CollectionPickerSheetView`) is presented as a nested SHEET from the map spot sheet.

## Map (Mapbox)

- The map engine is the Mapbox Maps SDK for iOS (native), integrated via Swift Package Manager and pinned to an exact v11 version (currently 11.19.0). The engine lives in Swift (`iosApp/iosApp/`), NOT in the shared module.
- `MapboxMapView` wraps the SDK's native SwiftUI `Map` and renders one category-colored pin per spot via `CircleAnnotationGroup` (pin color resolved shared-side from `SpotCategory`; no category hex hardcoded in Swift).
- Interaction uses the v11 `Interaction` API inside the `Map { }` content builder: `TapInteraction(.standardPoi)` adopts a tapped built-in POI (prefills name + category); a generic `TapInteraction`/`LongPressInteraction` handles taps on empty map to create a spot at that coordinate. POI-tap takes PRECEDENCE over the generic tap (featureset interactions resolve first; the POI handler returns `true` to stop propagation). Do NOT use the deprecated `.onMapTapGesture`/`.onMapLongPressGesture` modifiers.
- The app's OWN spot pins are now TAPPABLE: a tap on a spot pin (`CircleAnnotation.onTapGesture` returning handled) opens the lean `MapSpotSheetView` for that spot (whose action assigns it to a collection), and this takes PRECEDENCE over the empty-map create tap (the pin handler returns `true` to stop propagation) so a pin tap never starts a create flow. The POI-adopt + empty-map/long-press create flows are unchanged.
- Creating a spot (empty-map tap, the FAB at map center, or POI adoption) opens `AddSpotSheetView` following the standard sheet pattern. After a spot is created, the AddSpot flow prompts the user via a native SwiftUI `.alert` whether to also create a post for it; choosing to post opens `CreatePostView` with that spot preselected (the legacy spot→post flow).
- Tokens are never hardcoded: the public `pk.` runtime token comes from a gitignored `iosApp/Mapbox.xcconfig` (seeded from the committed `Mapbox.xcconfig.template`) surfaced into Info.plist as `MBXAccessToken`; a secret `sk.` download token, if required by the SDK fetch, goes in `~/.netrc` per the committed `netrc.template`.
- Route planning and search/geocoding are deliberately NOT implemented yet (planned later); Google Places is not used (single-vendor Mapbox).

## Backend (Supabase)

- Supabase is the backend. The supabase-kt SDK (GoTrue auth + Postgrest, 3.8.0; Ktor 3.5.1; kotlinx-serialization/coroutines 1.11.0) lives in the SHARED module. All supabase-kt / Ktor / coroutine / `suspend` / `Flow` types stay INTERNAL to shared — only flat types and callback-based hooks cross `FeedBridge`. The bridge's suspend/Flow/supabase work runs on a background `Dispatchers.Default` scope; only the final flat callback/listener is delivered on the main thread (via the `onMain` helper), consistent with the flat-boundary rule.
- Auth: email/password sign-up, sign-in, sign-out, and session restore via a shared `AuthRepository` over GoTrue, exposed through a flat callback-based bridge (completions of `Bool`/`String`; an `observeAuth` listener). An `@Observable` Swift `Session` wrapper (mirrors the `Localization` pattern) drives the AUTH GATE in `ContentView` (auth screens when logged out, `RootTabView` when logged in). Sign-up passes name/city in the user metadata so the DB trigger populates the profile.
- Keys/config: the PUBLIC publishable key (`sb_publishable_…`) + project URL come from a gitignored `iosApp/Supabase.xcconfig` (seeded from the committed `Supabase.xcconfig.template`), surfaced into Info.plist as `SupabaseURL` / `SupabasePublishableKey`, read at launch and injected via `FeedBridge.configureSupabase(url:publishableKey:)`. The URL is stored host-only (xcconfig `//` caveat; Swift re-adds the scheme). The secret/service-role key NEVER ships in the client. (Current terminology: Supabase's PUBLISHABLE key replaced the older "anon" key.)
- DB schema: SQL migrations under the repo-root `supabase/` dir (profiles + spots + posts/comments/votes) with the signup→profile trigger, `updated_at` triggers, and self-contained RLS (`spots` readable by any authenticated user; insert/update/delete own via `owner_id = auth.uid()`). The user provisions their own project and applies the migrations (`supabase link` + `supabase db push`).
- SQLDelight cache migrations: schema changes to the SQLDelight cache DB (`ThirdSpaceDb`) require a migration file at `shared/src/commonMain/sqldelight/com/example/thirdspace/db/migrations/<fromVersion>.sqm`, which auto-bumps the generated schema version so an existing on-device DB is migrated in place rather than crashing with `no such table`. The `.sq` continues to describe the current schema for fresh installs; `deriveSchemaFromMigrations` stays OFF. The current schema version is 4 (`1.sq` = v1, `1.sqm` → v2, `2.sqm` → v3, `3.sqm` → v4; `2.sqm` added the `cachedPosts.kind` column, `3.sqm` added `author_user_id` to `cachedPosts` + `cachedComments`). Collections intentionally add NO SQLDelight cache and NO `.sqm` (they use an in-memory seam like the follow/profile seams), so the schema version stays 4.
- Feed (posts / comments / votes) is backed by Supabase. Reads go through the `feed_entries` UNION VIEW (posts PLUS bare spots that have no post), NOT only `post_feed`. The flat boundary carries a `kind: String` ("post"/"spot") discriminator; bare-spot cards hide the vote control, comment button, and caption (`PostCardView` `isBareSpot`) while keeping the spot header. `post_feed` remains the source for the UNION's post branch and for the profile's own-posts (joins posts + profiles + spots; real `score` = sum of `post_votes`; the caller's own `my_vote` via `auth.uid()` under `security_invoker`). Writes: `createPost` inserts into `posts` (requires an existing `spot_id`; empty caption allowed as a pure check-in); `vote` writes `post_votes` (value CHECK ±1; clearing a vote DELETEs the row); comments insert into `post_comments`. All write paths are offline-first through `FeedCache` (SQLDelight) with outbound queues — `pendingPostInserts`, `pendingVotes` (latest-intent-wins per post), `pendingCommentInserts` — flushed on the next authenticated refresh; optimistic local rows are reconciled by a destructive replace-all on the post-push refresh. Comment author names resolve via a PostgREST `profiles(name)` embed with an honest empty-string fallback. Relative timestamps use the self-contained `RelativeTime` formatter, not the i18n `Strings` layer.
- Profile: the current user's own `profiles` row is read + edited via a shared `ProfileRepository` with an IN-MEMORY single-row cache (side-effect-free reads + explicit refresh, mirroring the feed/spots seams — NO SQLDelight / `.sqm` for the single row). Reads go through the bridge's flat `profile()` / `loadProfile` / `observeProfile`; `updateProfile(name,city,bio)` writes the own row under the existing RLS "update own" policy (optimistic in-memory update; offline/unauth reports failure, NO durable queue). The profile's `spotCount`/`postCount` are the real counts of the user's own `spots`/`posts`, DERIVED from the fetched own-content list sizes; its "meine Posts"/"meine Spots" tabs show the user's OWN rows (`post_feed` where `author_id == uid` / `spots` where `owner_id == uid`), reusing the shared `PostFeedMapping` / `SpotDtoMapping`. `username` is derived (email local-part; no DB column), `monthYear` is derived from `created_at`, and `bio` is a `profiles` column added by the `profile_add_bio` migration. The profile cache is reloaded/cleared driven by the iOS `ContentView`'s auth-state changes (`.onChange(of: session.isAuthenticated)` + `.onAppear`): sign-out clears the in-memory profile cache via a flat `FeedBridge.clearProfile()` → `Profiles.clear()` → `ProfileRepository.clear()`, so a different user signing in on the same launch never sees the prior user's profile/posts/spots (cross-user data-leak fix). The profile screen also has native pull-to-refresh (`ProfileView` `.refreshable`), analogous to the feed. `followerCount`/`followingCount` are the REAL counts of the current user's social graph, fetched from the `follows` table during the profile refresh and folded onto the cached `Profile` by `ProfileRepository` via injected follow-count providers (the same way spot/post counts are injected).
- Follow (social graph): a one-directional follow graph backed by a new `follows` table (migration `20260101000009_init_follows.sql`) — columns `follower_id`/`following_id` (both FK `auth.users` ON DELETE CASCADE) + `created_at`, a composite PK `(follower_id, following_id)` guaranteeing uniqueness + idempotent re-follow, a CHECK (`follower_id <> following_id`) preventing self-follow, and self-contained RLS (read-all to authenticated; insert/delete own via `follower_id = auth.uid()`; no UPDATE); two indexes back the followers-of / following-of list + count queries. The shared seam is a `FollowRepository` + `Follows` provider (mirrors `Profiles`/`Feed`: in-memory cache, side-effect-free pure reads, explicit refreshes on a background `Dispatchers.Default` scope with an in-flight coalesce guard, optimistic follow/unfollow with NO durable queue — offline/unauth keeps the optimistic state but reports `false`) over a `SupabaseFollowRepository` (`FollowRemoteSource`) using only proven Postgrest API — a client-side join (follow rows, then per-id `profiles` reads) rather than a two-FK embed, and `.decodeList().size` counts rather than `Count.EXACT`; the flat `FollowUser(id, name, username, city, isFollowedByMe)` model crosses the boundary as `IosFollowUser`. `SupabaseProfileRepository` was generalized with `fetchProfile(userId)` so ANY user's profile row can be read (not just the current user's). Live follow data still requires the user to apply the new migration + a logged-in session.
- Collections (personal spot collections): PERSONAL, owner-scoped spot collections backed by two new tables (migration `20260101000010_init_collections.sql`) — `collections` (id, `owner_id` FK `auth.users` ON DELETE CASCADE, name, created_at, updated_at + a `set_updated_at` trigger reused from the profiles migration) and a `collection_spots` many-to-many join (`collection_id` FK `collections` ON DELETE CASCADE, `spot_id` FK `spots` ON DELETE CASCADE, created_at, composite PK `(collection_id, spot_id)` for uniqueness/idempotent re-add; insert/delete only, no UPDATE). OWNER-SCOPED RLS (these are PRIVATE, unlike the read-all `spots`/`follows` tables): `collections` read/insert/update/delete gated `owner_id = auth.uid()`; the join table has no owner column so its RLS gates every op via an EXISTS against the parent collection's ownership. Indexes on `owner_id` + `collection_id` + `spot_id`. The shared seam is a `CollectionRepository` + `Collections` provider (mirrors `Follows`/`Profiles`: in-memory cache — NO SQLDelight — side-effect-free pure reads, explicit `Mutex`-coalesced refreshes on a background `Dispatchers.Default` scope, optimistic create/rename/delete/add-spot/remove-spot with NO durable queue — offline/unauth keeps the optimistic state but reports `false`; an optimistic create uses a local `temp-` id reconciled by a refresh on success) over a `SupabaseCollectionRepository` using only proven Postgrest API — a client-side join (fetch `collection_spots` rows then per-id resolve against `spots` reusing `SpotDtoMapping`) rather than an embed, and `.decodeList().size` counts rather than `Count.EXACT`; the flat `SpotCollection(id, name, spotCount, createdAtLabel)` model crosses the boundary as `IosSpotCollection`. Public/shared collections and an offline collection cache are DEFERRED; live collection data requires the user to apply the new migration + a logged-in session.
- Cache reads are SIDE-EFFECT-FREE: `getPosts`/`getComments`/`getSpots` only read the local cache and never trigger a remote fetch. A remote refresh is triggered ONLY explicitly — the bridge `loadFeed`/`loadComments`/`refreshSpots` hooks, pull-to-refresh, and a single reconciling refresh after a successful write push — coalesced by an in-flight guard.
- The one-directional follow graph IS implemented (see the Follow seam above). Deliberately deferred on the backend: Realtime, spot update/delete sync, advanced conflict resolution, and the broader legacy social graph (friendships (symmetric)/notifications/moments/DMs/moderation) are NOT implemented.

## Spots & offline seam

- `Spot` (commonMain) carries `lat`/`lng` (Double) and remains extensible for later fields (e.g. `description`, photo).
- `SpotCategory` (commonMain) is the single source of truth for the fixed category list, each category's map-marker color (`#RRGGBB`), and the Mapbox maki/POI-class → category mapping. Category LABELS are dynamic content and are NOT part of the i18n `Strings` layer (consistent with the existing not-translated convention for spot categories).
- The offline seam is now IMPLEMENTED. `SpotRepository` (commonMain) is backed by a `CachingSpotRepository` — the `Spots` provider builds it by default; `InMemorySpotRepository` remains a fallback/test impl. `CachingSpotRepository` composes a SQLDelight local cache (`cachedSpots` + a `pendingSpotInserts` outbound queue) with a `SupabaseSpotRepository` (Postgrest). Offline is a shared/cross-platform concern, so this lives in the shared module (Android can adopt it later).
- Reads are cache-first and synchronous, so `FeedBridge.spots()`/`addSpot` stay flat and unchanged and the SwiftUI map/create UI is untouched. A background coroutine does remote fetch → replace-all → flush the pending queue. Creates write through to the cache immediately and enqueue for remote push; offline / unconfigured / unauthenticated leaves items queued and never crashes. `owner_id` comes from the session. UI-only fields (`checkInCount`, `placeholderColorArgb`) are NOT persisted — they are re-derived on read via `SpotMapping`.
- Flat refresh hooks `FeedBridge.refreshSpots` / `observeSpots` exist (no-arg, main-thread) for live refresh; currently optional/unwired on the Swift side (the map reflects remote changes on next appearance). Real remote persistence requires the user's keys + applied migrations + a logged-in session.

## Deliberate exclusions (current state)

- Auth, spot persistence, the feed (posts/comments/votes), AND the profile are all backed by Supabase. `SampleData` no longer backs any live screen; it now only provides the OFFLINE SEED for the feed/spots caches (so they are not empty pre-login) plus the stable report-reason / map-filter keys.
- The profile edit page's "Konto" tab auth operations (change email, change password, delete account) and the avatar/banner upload are still placeholder/no-op — deferred.
- The one-directional follow graph IS implemented; the broader social graph (friendships (symmetric)/notifications/moments/DMs/moderation), Realtime, and spot update/delete sync remain out of scope.
- Personal spot collections ARE implemented (private, owner-scoped — see the Collections seam above); public/shared collections and an offline collection cache remain deferred.
- The spot model still lacks `description` and a photo strip (both intentionally absent for now); `SpotSheetView` uses placeholder content for those fields. Coordinates (`lat`/`lng`) do now exist.

## Verification

Automated/technical verification is governed by `verification-strategy.md`. iOS simulator Debug builds ARE runnable in this environment via `xcodebuild` and should be used to verify iOS/Swift changes; visual/layout QA remains the developer's responsibility. Shared backend logic (auth mapping, caching/queue) is unit-tested on both targets — including an in-memory SQLite round-trip on the Android host target — while real Supabase round-trips require keys + migrations + a logged-in session.
